## 2. 重点模块测试点展开：接口测试-权限与限流

该模块是本轮测试的深度体现（越权、限流、权限边界），6 条用例逐点设计如下：

| # | 测试点 | 测试方法 | 预期结果 | 关联用例 |
|---|---|---|---|---|
| 1 | 未登录访问限制 | 未登录状态下直接访问发帖/评论/个人中心页面与接口 | 页面跳转登录页；接口返回 401 未授权 | TC-013 / TC-020 / TC-041 |
| 2 | 管理接口越权 | 普通用户 Token 调用管理员接口（如 `/api/users`） | 返回 403 permission_denied | TC-042 |
| 3 | 删帖权限边界（水平越权） | 普通用户尝试删除**他人**的帖子/评论 | 操作被拒绝，返回 403 | TC-043 |
| 4 | 登录接口限流验证 | 循环调用 `POST /api/token`，观察是否触发限流 | 连续异常尝试应触发 429 或账号锁定 | TC-044 |
| 5 | 发帖接口限流阈值验证 | 登录后连续发布多个帖子，观察限流触发时机 | 触发 429，限流保护生效（阈值是否合理另见 BUG-003） | TC-045 |
| 6 | 写接口业务规则校验 | 调用发帖接口但不传板块标签（tags） | 返回 422 校验失败，标签为必填 | TC-046 |

> 测试点 4、5 是一组**对照设计**：同为限流，一个验证"该有限流的地方有没有"，一个验证"限流的阈值合不合理"。实际执行中两条均发现缺陷（BUG-002 / BUG-003）。
>
> 注意口径差异：测试点 5 的用例 **TC-045 执行结果为「通过」**（限流确实生效了），
> 而它暴露的"阈值过严"记为本模块的 BUG-003 —— **用例通过 ≠ 该测试点无缺陷**。

## 4. 测试环境

| 项 | 内容 |
|---|---|
| 被测系统 | 公开 Flarum 练习论坛（具体地址由环境变量 `FORUM_BASE` 指定） |
| 环境类型 | **线上生产环境**（非本地/独立测试环境，测试活动直接作用于线上） |
| 服务器 | 公网云服务器，配置未知（无服务器访问权限；性能结论仅代表当前环境，不代表生产能力） |
| 测试账号 | 普通用户账号（账号与口令通过环境变量配置，不在仓库中公开） |
| 工具链 | Python 3（pytest / requests / openpyxl / Playwright 1.62.0）、JMeter 5.6.3 |
| 浏览器 | Playwright 内置 Chromium 1.62.0；**仅覆盖 Chrome 内核，未做跨浏览器测试** |
| 网络 | 公网 HTTPS，测试时段网络正常 |

> **最大的测试约束是"线上生产环境"**：无数据库凭据、无服务器权限、测试操作会影响真实用户，本计划的风险与应对均围绕此前提设计（见第 9 节）。
>
> **环境性质（2026-09-22 事后补记，不改写上文）**：上表"线上生产环境"指的是
> **测试交流圈面向测试学习者开放的公开练习环境**（非商业生产系统）—— 在其上进行练习性测试
> 是站点开放的用途之一。第 9 节风险 4、5 所说的"真实用户"即该环境中的**其他学习者用户**，
> 应对措施（并发上限 20、避开高峰、凌晨执行）按此前提执行。本补记只补充性质说明，
> **不修改计划的任何原始表述与数字**（计划应定格在启动时）。

## 6. 准入条件

- ✅ 系统可访问，登录正常（UI + API 双通道已验证）
- ✅ 主链路（登录 → 浏览 → 搜索 → 发帖）可走通
- ✅ 无大面积 500 故障

---

## 7. 准出条件

1. 用例执行率 **≥ 95%**，且**未执行用例须逐条书面说明原因**（受缺陷阻断，或主动规避风险），不得存在无说明的阻塞项
2. 功能用例通过率 **≥ 90%**（已知缺陷除外）
3. 全部缺陷（P0–P3）录入缺陷报告，附复现步骤 + 截图 + 接口证据
4. **P0/P1 缺陷 100% 完成修复验证或风险知会**；因客观原因无法修复的，须标注原因并评估风险敞口
5. 接口自动化用例全部运行，**无意外失败**；已知缺陷用 xfail 严格标记（`xfail_strict=true`）
6. 性能测试完成 **3 档并发梯度**，错误率 **< 1%**
7. 交付物（计划 / 用例 / 缺陷 / 报告 / 脚本）**数字口径完全一致**

> 第 4 条的措辞说明：被测系统为第三方线上论坛，缺陷修复不由测试方控制。因此准出标准定为"修复验证**或**风险知会"，而非单方面的"修复率 100%"——后者在无代码修改权的项目上是不可能达成的指标。
>
> 第 1 条的措辞说明：线上生产环境存在**测试方不可控的阻断因素**（如被测系统自身的限流缺陷会把后续用例挡在门外）。把标准定为"执行率 100%"会导致一条用例被系统挡住就整体不达标，且容易诱使执行者把"没跑到"记成"通过/失败"来凑数。因此改为 **≥ 95% + 逐条说明**：既不放过无说明的烂尾，也承认"被阻断且已说明"是合规结果。

## 8. 缺陷等级定义

| 等级 | 定义 | 本次项目实例 |
|---|---|---|
| **P0 致命** | 系统崩溃、核心功能完全不可用、数据丢失 | 本次未发现 |

## 9. 风险与应对

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| 1 | 写接口限流 429 | 自动化脚本中断、造数据失败 | 脚本控频 + 重试；造数据控制频率；将限流异常标记为已知缺陷（xfail） |
| 2 | 无数据库凭据 | 无法直接验证数据落库一致性 | 通过 API 间接验证（发帖后查列表/详情确认数据存在） |
| 3 | 普通用户无硬删除权限 | 测试帖无法彻底删除，残留污染线上 | 测试帖统一加【测试】前缀；改用软删除（`isHidden`）清理；必要时请管理员处理 |
| 4 | **测试数据污染线上环境** | 影响真实用户体验、社区数据混乱 | 破坏性操作优先用 API 验证后立即清理；测试结束自查并软删除全部测试数据 |
| 5 | **性能压测影响线上其他用户** | 线上响应变慢，严重时服务不可用 | 并发上限控制在 20 以内；避开高峰时段；发现响应异常立即停止压测 |
| 6 | **账号被限流/封禁导致测试中断** | 测试无法继续，进度受阻 | 控制操作频率；限流后等待恢复；准备备用账号 |
| 7 | 发帖标签必选 | 用例执行时遗漏前置步骤导致误报 | 用例明确前置步骤（选板块/标签），并作为业务规则用例单独验证 |
