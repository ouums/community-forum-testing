> 登录三档 avg 293/575/1181ms，**低于**四个读接口的均值（307/679/1375ms，见下表），
> 也就是说单看"把一批偏快的请求移出样本"，剩余样本的均值反而会**略微上浮**（304 → 约 307ms）。

> 响应时间下降会盖过上面那点样本均值上浮。
>
> 无论偏哪一边，本文的 "TPS ≈ 15 是吞吐上限" 与 "响应随并发线性增长" 两条结论都不会被推翻；
> 各读接口自身的 avg/p90 也不受影响（它们的请求数未变）。

## 测试场景

仅压**读接口**（发帖写接口限流阈值过严——第2帖即429，BUG-003，写接口压测无意义）：

| 场景 | 接口 |
|---|---|
| 登录（**当时每轮循环都登录**，见顶部说明） | POST /api/token |
| 浏览首页 | GET /api/discussions?page[limit]=10 |
| 查看帖详情 | GET /api/discussions/463 |
| 搜索 | GET /api/discussions?filter[q]=123 |
| 板块标签 | GET /api/tags |

配置：Ramp-up 5s，无 Think Time（最坏情况），每用户循环 50 次，登录取 Token 后读接口带 Authorization 头。

## 总体指标

| 并发 | 总请求 | 错误 | 错误率 | 平均响应(ms) | TPS |

| 5 | 1250 | 0 | 0% | 304 | 15.7 |
| 10 | 2500 | 0 | 0% | 658 | 14.7 |
| 20 | 5000 | 0 | 0% | 1336 | 14.7 |

## 各接口响应时间（ms）

| 接口 | 5并发 avg / p90 | 10并发 avg / p90 | 20并发 avg / p90 |
|---|---|---|---|
| 登录 | 293 / 368 | 575 / 702 | 1181 / 1444 |
| 浏览首页 | 267 / 341 | 628 / 711 | 1272 / 1523 |

| 板块标签 | 136 / 170 | 249 / 315 | 686 / 912 |

## 结论

1. **系统在 20 并发内稳定可用**：三档并发 0 错误率、无连接异常、无超时。
2. **响应时间随并发线性增长**：5→10→20 并发，平均响应约每档翻倍（304→658→1336ms），符合单节点 PHP-FPM + MySQL 的串行处理特征，无横向扩展能力。
3. **吞吐瓶颈约 15 TPS**：并发从 5 提到 20，TPS 几乎不变（15.7→14.7），说明系统吞吐在并发 5 时已到上限，受限于服务器资源/DB。
4. **搜索接口是性能热点**：三档并发下均最慢（20并发 p90 达 2.4s），推测为 DB 全表 LIKE 查询无索引（与 BUG-001 中文搜索失效同源）。
5. **标签接口最快**：p90 始终 < 1s，可能命中缓存。
6. 对比单用户基线（首页 535-693ms）：5 并发时因 HTTP keep-alive 连接复用反而更快（267ms）；20 并发时劣化至 2.4 倍。

## 建议

- 搜索接口需加索引/改全文检索（MySQL FULLTEXT 或专用搜索），预期可将 20 并发 p90 从 2.4s 降至 <500ms。
- 若需支撑更大并发，需横向扩展（多实例 + Redis 缓存 + DB 读写分离）。
